# 与 AI 协作完成 kubeai 平台的过程记录

> 这份文档是为招聘系统里「请描述一个与 AI 协作完成的项目或任务」这个问题准备的，同时也作为
> 仓库的一部分提交，方便面试时对照代码核查。文中每个结论都能在仓库里找到对应的代码、测试或
> 基准数据。

## 一、项目背景

我投递的岗位是云原生 AI 平台研发，JD 里的四件事是：**模型训练与推理工作流的设计开发**、
**训练引擎与推理引擎建设**、**GPU/NPU 算力调度与资源利用率**、**技术文档编写**。

我原来的经历集中在「用 LangChain/FastAPI 做大模型应用」。应用层和平台层的差别在于：应用层关心
接口跑通，平台层要回答「这张卡还剩多少显存、这批任务怎么排、为什么吞吐上不去」。我需要一个能把
这三件事放在同一个上下文里讲清楚的项目，于是决定自己写一个：

> **kubeai** —— 一个云原生 AI 平台：GPU 感知调度器 + DAG 工作流引擎（可编译为 Argo Workflows
> 与 Kubeflow PyTorchJob）+ OpenAI 兼容的连续批处理推理网关。

约束条件（也是我给自己定的验收标准）：

1. **本机就能跑通、能测**，不需要 K8s 集群、不需要下载模型权重；
2. **性能结论必须是可复现的数字**，不能是「明显更快」这种说法；
3. 交付物要能被别人接手：测试、CI、容器镜像、Helm chart 都要有。

## 二、AI 在项目里承担了什么

我把 AI 当作一个**能立刻给出草案、但必须由我验证的协作者**，而不是代码生成器。具体分工：

| 环节 | AI 负责 | 我负责 |
|---|---|---|
| 架构选型 | 给出三种子系统划分方案及其取舍 | 决定按「放置 / 编排 / 服务」切分，理由是三者共享同一个硬件模型 |
| 编码 | 按我给出的接口签名和约束生成实现草案 | 定义接口、审每一处数值逻辑、补错误处理与边界条件 |
| 调试 | 根据报错和现象提出假设 | 设计能证伪假设的最小实验，确认根因后再改 |
| 性能 | 生成微基准脚本模板 | 判断「该测什么」，读数据、下结论、定优化优先级 |
| 文档 | 起草结构 | 核对每个数字与代码一致，删掉无法复现的说法 |

真正省时间的是**草案速度**：一个连续批处理的调度循环、一个 Argo 编译器的映射表，AI 几秒钟就能
给出可用骨架，我省下的是打字时间，省不下的是判断时间。

## 三、遇到的问题与解决过程

下面四个是 AI 协作过程中真正花时间的部分。**每一个都是 AI 先给出「看起来对」的版本，由我测出来
是错的。**这也是我认为这段经历值得写的原因。

### 问题 1：批处理让吞吐不升反降

**现象**：第一次跑基准，`batch=32` 的连续批处理只有 101.8 tok/s，反而比「一个一个跑」的
146.0 tok/s 更慢。按常识批处理应该更快。

**AI 的第一反应**是「模型太小，开销占比高，把模型调大一点」。这个解释听起来合理，但我先做了一个
动作：**把批次层和调度层分开测**。

```
backend-only decode scaling（没有 batcher、没有队列、没有指标）
batch=1   5.87 ms/step   170.4 tok/s   1.00x
batch=8  27.45 ms/step   291.4 tok/s   1.71x
batch=32 90.60 ms/step   353.2 tok/s   2.07x
```

后端批处理本身有 2.07 倍加速 —— 说明「模型太小」不是原因，问题出在调度层。

**根因**：我自己写的静态批处理基线是错的。代码里每轮都把已完成的序列从批次里移除：

```python
active = [r for r in active if not r.finished]   # 这已经不是静态批处理了
```

真正的静态批处理是**整组一起解码到最后一个完成**，提前结束的序列仍然占着槽位、仍然被算一遍。
改对之后，结论完全反转：

| 场景 | 吞吐 | 相对串行 | 槽位效率 |
|---|---:|---:|---:|
| 静态批处理 batch=32 | 101.8 tok/s | 0.70× | 0.543 |
| 连续批处理 batch=32 | 180.9 tok/s | 1.24× | **1.000** |

**静态批处理比不批处理还慢 30%**，因为一半以上的算力花在已经结束的序列上。连续批处理是它的
**1.78 倍**。

> **收获**：一个跑得通、但没有正确实现基线的性能测试，比没有测试更危险 —— 它会让你得出反向结论。
> 我为此加了一个 `slot_efficiency` 指标（实际产生的 token / 消耗的 (step, sequence) 槽位），
> 让「浪费」变成可以直接读出来的数字，而不是靠推理判断。

### 问题 2：`spread` 策略一个任务都调度不出去

**现象**：`kubeai schedule --policy compare` 输出里，`binpack` 完成 59 个任务，`spread` 和
`topology-aware` 完成 **0 个**，平均利用率 0.000。

**AI 的建议**是「检查 SpreadPolicy 的评分函数」。我去看了评分函数，逻辑没问题。于是我换了个方向：
**把三个策略拆开、各自用全新的集群跑一遍**。结果三个都能正常工作。

**根因**：`Scheduler` 直接原地修改传入的 `Node`/`DeviceSlot` 对象。而 `compare_policies` 把
**同一个集群对象**传给了三次仿真 —— 第一个策略跑完，显存还没释放，后面两个策略面对的是一个几乎
占满的集群。测的不是策略，是上一个策略的残留。

**修复**：每个策略拿一份 `copy.deepcopy` 的集群；顺便把「到达时间」从共享的 `TaskRequest` 上
挪到仿真内部的局部字典，避免同一份 workload 被多次回放时互相污染。

### 问题 3：仿真里 200 个任务只完成 59 个

修完问题 2，三个策略都能跑了，但完成数还是只有 59/200，而且 makespan 一律顶到 2000 秒的时间上限。

**AI 提出**「把 max_time 调大」。我不同意 —— makespan 顶到上限说明仿真没有自然结束，调大只会让
数字更大更难看。我改成去查「哪些任务永远排不上」。

查出两个独立缺陷：

1. **workload 生成器会生成不可能满足的请求**：`pretrain` 类别随机出 32768 MiB/卡，而默认集群的卡
   只有 24564 MiB。这些任务永远 pending，导致仿真跑不到自然结束，`avg_utilization` 被 2000 秒的
   空转尾巴稀释成 0.024。
2. **`Scheduler.release()` 不归还 CPU 和 host memory**。代码里留着两个占位变量：

   ```python
   task_cpu = 0        # 早期草稿的残留
   task_mem = 0
   node.cpu_millicores_allocated = max(node.cpu_millicores_allocated - task_cpu, 0)
   ```

   显存正常释放，所以小规模测试完全看不出来；但 CPU 额度只增不减，跑久了每个节点都会因为
   「lacks cpu」拒绝一切任务。这个 bug 只在长仿真里暴露。

**修复后**：200/200 全部完成，平均利用率 0.65–0.73，makespan 收敛到 661 秒。

> **收获**：「把超时调大」是掩盖问题的典型做法。**makespan 顶到上限本身就是最强的失败信号**，
> 它说明系统停在了不可能推进的状态里。我加了一条显式判据：*如果没有任何分配被持有、又没有任何任务
> 能被放置，那就永远不可能有进展* —— 直接结束仿真，而不是空转到时间上限。同时补了两个测试，
> 一个专门验证 `release` 会归还 CPU/内存，一个验证 CPU 耗尽时节点会被正确拒绝。

### 问题 4：TTFT 算出 36 秒，物理上不可能

**现象**：连续批处理 `batch=32` 的平均首 token 延迟报出 36 秒。但整轮工作只有 864 个 token、
按 180 tok/s 算是 5 秒 —— **首 token 延迟不可能超过总时长**。数字自己就不自洽。

**根因**：整个基准脚本只在开头取了一次「突发到达时刻」，之后串行、静态、连续三个场景共用这个
锚点。后两个场景的首 token 延迟里，混进了前面场景的全部运行时间。

**修复**：每个场景各自取一次锚点。修完后数字变得可解释：`batch=32` 的 TTFT 从 36 秒降到 0.56 秒。

> **收获**：这个 bug 是**用物理约束发现的，不是用调试器发现的**。看到指标违反常识时，先做量纲和
> 数量级检查，比逐行读代码快得多。

### 附带发现：我的技能词表只覆盖了 10% 的中文

写测试时发现 `"云原生推理平台"` 经过 tokenizer 往返变成 `"云原台"`。原因是词表只映射了
U+4E00–U+53FF 这 2048 个汉字，而 CJK 统一表意文字区有 20992 个。修掉之后同一段中文可以完整往返。
这个 bug 不影响性能，但如果用它做演示，任何人第一眼就会看到乱码。

## 五、我认为 AI 协作真正的边界在哪

三条结论，都是这个项目里踩出来的：

1. **AI 很擅长写「看起来对」的代码，不擅长否定自己的产出。** 四个主要 bug 里有三个在 AI 给出的
   版本里是自洽的 —— `release()` 里的 `task_cpu = 0` 语法没毛病、静态批处理那段代码逻辑也没毛病，
   只有跑出数字才看得出来。
2. **所以我的时间主要花在「设计能证伪的实验」上，而不是写代码上。** 把后端和调度层分开测、把三个
   策略拆开各自跑一遍 —— 这两个动作各自只用了不到十分钟，但它们直接把猜测变成了证据。
3. **可复现的数字是唯一可信的交付物。** README 里每个性能数字都由 `make bench` 生成，
   CI 里还有一条断言：如果连续批处理相对串行的加速掉到 1.2 倍以下，构建直接失败。这样「批处理
   是有效的」就不再是一句写在文档里的话，而是一条会被持续验证的约束。

## 六、后续计划

按优先级：

1. **Paged KV cache（block table）**。目前每一步都要把 KV cache 补齐到批次内最长序列再拼接，
   后端单步 90.6 ms 里有相当一部分花在这上面 —— 这正是 vLLM 提出 PagedAttention 要解决的问题，
   也是当前最大的性能天花板。
2. **Chunked prefill / 批量 prefill**。目前 prefill 是逐条做的，prompt 长的流量下 TTFT 会偏高。
3. **真正的 device plugin + controller**。现在调度器是进程内对「建模的集群」做决策，与
   Kubernetes API 之间还差一个调谐循环。
4. **用生产 trace 回放替代合成分布**做调度评估。
